A **chatbot** is a conversational interface, **RAG** grounds answers in your own data, and an **agent** uses tools to take actions. Most businesses need RAG first: accurate, cited answers from their own content, which takes **4–6 weeks** to reach production. Add an agent only where taking actions earns its cost; a production agent takes **6–10 weeks** for one workflow (12+ across several systems) and spends tokens on every step.

## What is the difference between a chatbot, RAG and an agent?

The three are layers, not rivals. A chatbot is how users talk to the system. RAG is how the system knows things. An agent is how it does things.

- **Chatbot.** A conversational interface. A scripted chatbot follows a decision tree; a plain LLM chatbot answers from whatever the model learned in training, which means it will make things up about your products and policies.
- **RAG (retrieval-augmented generation).** Before answering, the system retrieves relevant passages from your documents and data and passes them to the model, so answers are grounded and can cite their sources. Our guide to [building a RAG pipeline](/blog/building-a-rag-pipeline) covers how it works.
- **Agent.** The model is given tools (search, APIs, database writes) and decides which to call, observes the result, and repeats until the task is done. This reason-act loop was described in the [ReAct paper](https://arxiv.org/abs/2210.03629), which had models generate reasoning traces and task-specific actions in an interleaved manner.

Anthropic's guide to [building effective agents](https://www.anthropic.com/engineering/building-effective-agents) adds a useful middle category. **Workflows** are systems where LLMs and tools are orchestrated through predefined code paths; agents choose their own path. Many problems that sound like they need an agent are really workflows: the steps are known, only the content varies. We go deeper on that distinction in [agentic AI workflows explained](/blog/agentic-ai-workflows-explained).

| | Chatbot | RAG assistant | AI agent |
| --- | --- | --- | --- |
| What it does | Holds a conversation | Answers from your content, with citations | Plans and takes actions through tools |
| Knows your data | Only what is scripted | Yes, retrieved per question | Yes, through retrieval and tool calls |
| Changes anything | No | No | Yes |
| Model calls per request | None (scripted) or one | One generation, plus a search | Many: one per step |
| Typical failure | Makes things up | Wrong or stale answer from poor retrieval | Wrong action, loops, runaway cost |
| Production timeline | Prototype in 1–2 weeks | 4–6 weeks | 6–10 weeks for one workflow; 12+ across several systems |

## Which one does your business need?

Walk down this table and stop at the first row that solves your problem. Each row down adds cost, build time and risk.

| If you need to... | Build | Why |
| --- | --- | --- |
| Answer a fixed set of questions with approved wording | Scripted chatbot or FAQ search | Predictable, cheap, nothing to hallucinate |
| Answer questions from docs, policies or product data | RAG assistant | Accurate answers that change when the documents change |
| Answer using the customer's own records (order status, account details) | RAG plus read-only tool calls | Still a workflow: the lookup is a fixed step, not a decision |
| Run a known multi-step process (classify, route, draft a reply) | Workflow with LLM steps | Steps are fixed in code, so it is testable and cheap |
| Complete open-ended tasks where the steps vary case by case, across several systems | Agent with approval gates | Only here does letting the model choose the path pay off |
| Make irreversible or regulated decisions (payments out, contracts, hiring) | Agent that drafts, person who decides | The model prepares the work; a person carries it out |

If the process is fully deterministic and the inputs are structured, you may not need an LLM at all; our comparison of [AI agents and RPA](/blog/ai-agents-vs-rpa) covers when rule-based automation is the better tool.

## How do costs compare: per conversation or per task?

A chatbot or RAG assistant costs money **per conversation turn**: one model call with the question and a handful of retrieved passages. The cost is easy to forecast: tokens per turn multiplied by conversation volume.

An agent costs money **per task**, and the task cost is less predictable. Every step is a separate model call, and each call re-sends the system prompt, the tool definitions and the growing history of earlier steps and tool results. Tokens therefore grow faster than the number of steps. [Anthropic puts it plainly](https://www.anthropic.com/engineering/building-effective-agents): the autonomous nature of agents means higher costs, and the potential for compounding errors.

An illustrative comparison, using round numbers rather than measurements:

| | RAG answer | Agent task (8 steps) |
| --- | --- | --- |
| Model calls | 1 | 8 |
| Input tokens per call | About 4,000 (instructions plus retrieved passages) | Starts near 3,000 and grows to about 12,000 as tool results pile up |
| Total input tokens | About 4,000 | About 60,000 |
| Output tokens | About 300 | About 2,000 (tool calls, reasoning, final result) |
| What drives the bill | Conversation volume | Steps per task, retries and task volume |

On those assumptions the agent task uses roughly fifteen times the input tokens of a RAG answer, before any retries. That is fine when the task replaces several minutes of a person's time, and wasteful when a single retrieval would have answered the question. Three practical rules follow:

1. **Compare cost per completed task with the cost of a person doing it**, not with the cost of a chatbot message.
2. **Cap steps, tokens and time per task in code**, so a loop cannot run up a bill.
3. **Cut the per-step cost** with prompt caching for the fixed system prompt and tool definitions, a cheaper model for routine steps, and trimmed histories. [Reducing LLM API costs](/blog/reduce-llm-api-costs) covers these levers, and [the cost of building an AI agent](/blog/cost-to-build-ai-agent) covers the build side.

## What are the risks, and where do approval gates belong?

Each layer adds a new kind of failure:

- **Chatbots** say wrong things, which is a reputational and sometimes legal problem.
- **RAG assistants** give stale or wrong answers when retrieval is poor, and leak data when permissions are not applied at retrieval time. [Reducing LLM hallucinations](/blog/reduce-llm-hallucinations) covers the answer-quality side.
- **Agents** take wrong actions. OWASP lists this as [Excessive Agency](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/) in its Top 10 for LLM applications, tracing it to excessive functionality, excessive permissions and excessive autonomy. Its guidance: limit the permissions an agent's tools have to the minimum necessary, and require a human to approve high-impact actions before they are taken.

Put the gate where the cost of a mistake changes:

| Action type | Example | Gate |
| --- | --- | --- |
| Read-only lookup | Check order status, search the CRM | None; log every call |
| Reversible, low-value write | Add a tag, create a ticket, save a draft | Automatic, with an audit log and undo |
| Customer-facing message | Send an email or reply to a customer | Human approves until quality is proven, then sample |
| Money or data changes | Issue a refund, change a plan, delete records | Human approval, or hard limits enforced in code |
| Irreversible or regulated | Payments out, signing, hiring decisions | Agent drafts only; a person executes |

Three rules make the gates real. Enforce them in code and in the downstream systems, never only in the prompt. Give the agent its own narrowly scoped credentials. And treat every retrieved document, email or web page as data, not instructions, because text inside them can try to redirect the agent (prompt injection).

## How do they combine in a real system?

Production systems usually layer all three. A support assistant might use a chat interface, answer how-to questions with RAG over the help center, look up order status with a read-only tool, and draft a refund for a person to approve. Only that last step is agentic, and it is gated. Our guide to [building a support chatbot with RAG](/blog/ai-customer-support-chatbot-rag) shows where the escalation lines sit.

Our own builds sit at different points on this spectrum. The [AI business consultancy chatbot](/work/ai-business-consultant-chatbot) is a conversational advisor that asks targeted questions and returns recommendations across marketing, HR, finance, operations, strategy and IT. The [contract analysis system](/work/legal-contract-ai) uses a multi-agent RAG pipeline to turn 500 to 1,000 page legal contracts into a queryable knowledge base that answers with cited sources: agents in service of retrieval, not agents taking actions.

The common mistake runs the other way: building an autonomous agent when a grounded RAG assistant would have solved the problem more reliably and for a fraction of the running cost. Start with the simplest layer that works and add tools one at a time, each with its own evaluation cases. [How long an AI agent takes to build](/blog/how-long-to-build-ai-agent) breaks down where the extra weeks go.

## Frequently asked questions

### What's the difference between an AI agent and a chatbot?

A chatbot is a conversational interface that responds to messages. An agent uses tools to take actions: calling APIs, updating records, running multi-step workflows, and deciding the next step from each result. An agent can sit behind a chat interface, but most chatbots do not need agentic autonomy.

### Do I need an AI agent or just RAG?

If you need accurate answers from your own data, RAG behind a chat interface is usually enough, and it is cheaper and easier to test. Add an agent only where taking real actions across systems adds value, starting read-only, with approval gates on anything that changes data and an evaluation set for every tool.

### Is RAG the same as a chatbot?

No. RAG is a technique for grounding a model's answers in your documents; a chatbot is one interface that can use it. RAG also powers search, summaries and agents that never hold a conversation.

### Why do AI agents cost more to run than chatbots?

Because an agent makes a model call for every step of a task, and each call re-sends the instructions, tool definitions and the history so far. One task can use many times the tokens of a single RAG answer, and retries add more. Measure agents by cost per completed task and cap steps and spend in code.

### Can an AI agent act without human approval?

For read-only lookups and small, reversible actions, yes, with logging. For anything that moves money, changes customer data, sends messages on your behalf or cannot be undone, keep a person approving until the evidence supports more autonomy, and enforce limits in code rather than in the prompt.

### Can we turn a RAG chatbot into an agent later?

Yes, and it is usually the better order. A RAG assistant gives you the retrieval, evaluation set and logging an agent needs anyway. Adding tools one at a time on top of it, each with its own test cases and gates, is lower risk than starting with an autonomous agent.
